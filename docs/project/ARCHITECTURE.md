# Architecture

Next.js App Router / React / TypeScript. app/page.tsx renders curriculum and the client terminal. lib/linux-simulator.ts is a pure per-attempt SIMULATED state machine; no subprocess or external networking occurs.

The simulator models scenario definitions plus two incident families. `file-access` incidents carry file mode state. `tcp-service` incidents carry both `processRunning` and a simulated `listenerPort`, allowing two connection-refused cases to share the same learner-facing prompt while process/socket observations discriminate the causes. `LabState` separates raw observations from causal hypothesis, repair provenance, verification, explanation and a bounded causal-transfer answer.

Differential sequencing is explicit state rather than UI inference. `LabState` stores `differentialOrder` (`listener-first` or `process-first`) and `differentialStep` (0 or 1). The pure simulator exposes deterministic mapping from order+step to the concrete scenario and never calls Date.now/Math.random/Web Crypto during state transitions. The React boundary chooses a fresh order with `window.crypto.getRandomValues` only when a fresh practice is created or the learner performs a full restart. Current-case `reset` preserves order and step. Refresh restores the persisted assignment.

The two TCP differential cases intentionally expose the same title, summary, README, symptom command and evidence commands. One starts with a live process listening on 9090; the other starts with no process and no owned LISTEN socket. Repair syntax is omitted from `help` until the learner has collected all observations and locked a hypothesis. Normal UI copy/buttons do not reveal which cause was assigned first. The assignment is still client-visible through developer tools because localStorage is not a secrecy boundary.

lib/practice-persistence.ts stores a browser localStorage checkpoint with practice schema version 6 and Linux fixture version 5. Schema moved from 5 to 6 because counterfactual answer/pass state and differential-completion semantics are persisted; fixture version stays 5 because the four incident definitions, initial states and command outputs are unchanged. Restore validates scenario/order/step consistency, scenario-family/case compatibility, process/listener tuples, observations, hypothesis/repair invariants, target state, structured reasoning, causal-transfer shape/match, allowed transfer carry and derived completion flags. Stale schema-v5 or older, corrupt or semantically impossible checkpoints are discarded. If storage is unavailable the lab falls back to ephemeral state. Terminal transcript is intentionally not persisted; bounded scenario-scoped pre-repair snapshots and structured drafts are persisted. Client checkpoint data is untrusted practice state, not authoritative mastery.

Production-browser verification is configured in playwright.config.cjs. CI builds first, installs exact-pinned @playwright/test 1.63.0 plus Chromium under runner temporary storage, then Playwright starts the built app with `next start` on dedicated loopback port 3100, waits for readiness, runs three serial Chromium tests with one worker and owns server cleanup. `reuseExistingServer` is false. Failure diagnostics retain trace/screenshot output for artifact upload.

Browser test 1 covers the listener-first full learning flow, including guided file access, permission transfer, wrong causal hypotheses, repair-help hiding, exact repairs, explanations, wrong/correct counterfactual attempts, transfer-edit revocation and completed-state refresh. Browser test 2 starts from an explicit process-first assignment, completes both differential causes in reversed order and requires the listener counterfactual before final completion. Browser test 3 covers valid schema-v6 hydration, reset assignment preservation, contradictory assignment rejection, full restart, corrupt/stale-v5 checkpoint rejection, unavailable Storage API, mobile overflow, keyboard focus and console/page errors.

Future real-execution boundary remains: browser -> learning API -> authenticated lab gateway -> disposable isolated runtime -> verifier. The web host never executes learner commands.
No durable or server-trusted mastery is claimed. See ../DEVOPS_PLATFORM_ARCHITECTURE.md for the longer baseline. docs/plan is historical film planning, not active architecture.


## Evidence-linked reasoning

`preRepairEvidence` holds immutable records captured by actually executed diagnostic commands while the incident is initial. Records carry scenario, source slot, phase, command and output. Post-repair commands may mark observations viewed and show new output, but never create/overwrite before-repair snapshots. `evidenceReady` requires all three canonical snapshots. The hypothesis is immutable until reset.

`reasoning` is null or a structured draft: symptom/identity/resource each pair an evidence ID with a typed factual claim. A mechanism pairs exactly two distinct identity/resource evidence IDs with a typed relation; a target states the minimally sufficient mode/port. Permission identity facts encode UID and group names (`UID:GROUPS`), while the access-class inference lives in the two-source mechanism. TCP facts encode refused, process presence and observed port/none. The deterministic rubric validates every required source and claim; correct labels cannot compensate for wrong references/facts. Source pairs may be reversed, but duplicates, irrelevant symptom support and select-all arrays fail.

Editing persists the draft and revokes explained completion until resubmission. Explanation is available only after evidence-backed repair and exact target verification. Repair clears the draft; reset/restart/advance create clean snapshot/reasoning state. Checkpoint hydration validates source payloads against the current fixture, initial observation/snapshot consistency, strict reasoning shape and explained-state rubric. Validation protects internal consistency, not authenticity against developer-tool forgery.


## Causal counterfactual transfer

After the `differential-listener` case is repaired, verified and correctly explained, the UI asks one changed-evidence question. The original process and socket snapshots remain the evidence sources: process is present and the observed listener is 9090. The hypothetical changes only the socket observation to 127.0.0.1:8080 while holding process presence fixed. The deterministic rubric then requires prediction token `200`, repair-need token `none`, and causal relation `listener-target-match`.

The transfer answer stores explicit original process/socket source IDs and facts separately from the hypothetical prediction. A correct prediction cannot compensate for a wrong source or wrong original fact. Editing either the listener explanation or the transfer answer revokes dependent completion until rechecked. In listener-first order, a passed transfer is carried into the second process case so that resetting that later case does not erase already completed listener work. In process-first order, the listener is second and final completion remains blocked until the transfer gate passes.

This is intentionally one narrow deterministic perturbation. It does not simulate a new runtime state, execute a second network experiment, or prove general causal transfer. The next validation target should use a materially different changed-evidence relation rather than adding synonyms for the same listener answer.
