# Architecture

Next.js App Router / React / TypeScript. app/page.tsx renders curriculum and the client terminal. lib/linux-simulator.ts is a pure per-attempt SIMULATED state machine; no subprocess or external networking occurs.

The simulator models scenario definitions plus two incident families. `file-access` incidents carry file mode state. `tcp-service` incidents carry both `processRunning` and a simulated `listenerPort`, allowing two connection-refused cases to share the same learner-facing prompt while process/socket observations discriminate the causes. `LabState` separates raw observations from causal hypothesis, repair provenance, verification, explanation and two bounded causal-transfer answers: permission identity and listener/socket.

Differential sequencing is explicit state rather than UI inference. `LabState` stores `differentialOrder` (`listener-first` or `process-first`) and `differentialStep` (0 or 1). The pure simulator exposes deterministic mapping from order+step to the concrete scenario and never calls Date.now/Math.random/Web Crypto during state transitions. The React boundary chooses a fresh order with `window.crypto.getRandomValues` only when a fresh practice is created or the learner performs a full restart. Current-case `reset` preserves order and step. Refresh restores the persisted assignment.

The two TCP differential cases intentionally expose the same title, summary, README, symptom command and evidence commands. One starts with a live process listening on 9090; the other starts with no process and no owned LISTEN socket. Repair syntax is omitted from `help` until the learner has collected all observations and locked a hypothesis. Normal UI copy/buttons do not reveal which cause was assigned first. The assignment is still client-visible through developer tools because localStorage is not a secrecy boundary.

lib/practice-persistence.ts stores a browser localStorage checkpoint with practice schema version 7 and Linux fixture version 5. Schema moved from 6 to 7 because permission-transfer draft/pass state and progression/completion semantics are persisted; fixture version stays 5 because the four incident definitions, initial states and command outputs are unchanged. Restore validates scenario/order/step consistency, scenario-family/case compatibility, process/listener tuples, observations, hypothesis/repair invariants, target state, structured reasoning, both transfer shapes/matches, allowed carry and derived completion flags. Every differential checkpoint requires a canonical passed permission gate. Stale schema-v6 or older, corrupt or semantically impossible checkpoints are discarded. If storage is unavailable the lab falls back to ephemeral state. Terminal transcript is intentionally not persisted; bounded scenario-scoped pre-repair snapshots and structured drafts are persisted. Client checkpoint data is untrusted practice state, not authoritative mastery.

Production-browser verification is configured in playwright.config.cjs. CI uses the exact-locked @playwright/test 1.63.0 from npm ci/audit, builds, installs its selected Chromium runtime, then Playwright starts the built app with `next start` on dedicated loopback port 3100, waits for readiness, runs eight serial Chromium tests with one worker and owns server cleanup. `reuseExistingServer` is false. Failure diagnostics retain trace/screenshot output for artifact upload.

Browser test 1 covers the listener-first full learning flow, including guided file access, permission transfer, wrong/correct permission counterfactual attempts, edit revocation, wrong causal hypotheses, repair-help hiding, exact repairs, listener counterfactual attempts and completed-state refresh. Browser test 2 starts from an explicit process-first assignment, completes both differential causes in reversed order and requires the listener counterfactual before final completion. Browser test 3 covers valid schema-v7 hydration, reset assignment preservation, contradictory assignment rejection, full restart, corrupt/stale-v6 checkpoint rejection, unavailable Storage API, mobile overflow, keyboard focus and console/page errors.

Future real-execution boundary remains: browser -> learning API -> authenticated lab gateway -> disposable isolated runtime -> verifier. The web host never executes learner commands.
No durable or server-trusted mastery is claimed. See ../DEVOPS_PLATFORM_ARCHITECTURE.md for the longer baseline. docs/plan is historical film planning, not active architecture.


## Evidence-linked reasoning

`preRepairEvidence` holds immutable records captured by actually executed diagnostic commands while the incident is initial. Records carry scenario, source slot, phase, command and output. Post-repair commands may mark observations viewed and show new output, but never create/overwrite before-repair snapshots. `evidenceReady` requires all three canonical snapshots. The hypothesis is immutable until reset.

`reasoning` is null or a structured draft: symptom/identity/resource each pair an evidence ID with a typed factual claim. A mechanism pairs exactly two distinct identity/resource evidence IDs with a typed relation; a target states the minimally sufficient mode/port. Permission identity facts encode UID and group names (`UID:GROUPS`), while the access-class inference lives in the two-source mechanism. TCP facts encode refused, process presence and observed port/none. The deterministic rubric validates every required source and claim; correct labels cannot compensate for wrong references/facts. Source pairs may be reversed, but duplicates, irrelevant symptom support and select-all arrays fail.

Editing persists the draft and revokes explained completion until resubmission. Explanation is available only after evidence-backed repair and exact target verification. Repair clears the draft; reset/restart/advance create clean snapshot/reasoning state. Checkpoint hydration validates source payloads against the current fixture, initial observation/snapshot consistency, strict reasoning shape and explained-state rubric. Validation protects internal consistency, not authenticity against developer-tool forgery.


## Causal counterfactual transfer

After the `transfer` permission case is repaired to the minimal mode 640, verified and correctly explained as group-read, the UI asks a permission identity counterfactual. The original sources remain the worker identity and file metadata. The hypothetical holds `root:web` and mode `640` fixed but removes `report-worker` from group `web`. The deterministic rubric requires prediction token `403`, repair need `required` and causal relation `group-membership-required`. Wrong original source/fact, fixed mode, hypothetical identity, prediction, repair need or relation fails. A passed gate is required to enter and continue through differential diagnosis; editing/resetting the transfer case revokes it, while valid later differential resets preserve it.

After the `differential-listener` case is repaired, verified and correctly explained, the UI asks one changed-evidence question. The original process and socket snapshots remain the evidence sources: process is present and the observed listener is 9090. The hypothetical changes only the socket observation to 127.0.0.1:8080 while holding process presence fixed. The deterministic rubric then requires prediction token `200`, repair-need token `none`, and causal relation `listener-target-match`.

The transfer answer stores explicit original process/socket source IDs and facts separately from the hypothetical prediction. A correct prediction cannot compensate for a wrong source or wrong original fact. Editing either the listener explanation or the transfer answer revokes dependent completion until rechecked. In listener-first order, a passed transfer is carried into the second process case so that resetting that later case does not erase already completed listener work. In process-first order, the listener is second and final completion remains blocked until the transfer gate passes.

These are intentionally two narrow deterministic perturbations across different causal relations. Neither simulates a new runtime state or proves general causal transfer. Adding more fixed token variants now has diminishing learning value. The browser-runtime reproducibility debt is delivered; the pre-repair Git rationale is delivered; the next frontier is unfamiliar Git merge-graph causality.


## Git & CI simulated vertical slice

`lib/ci-simulator.ts` is a second pure browser-side state machine, intentionally separate from `lib/linux-simulator.ts`. Its artifact state models one CI producer/consumer contract incident rather than pretending a Linux command fixture is a generic DevOps runtime. `components/CiLab.tsx` renders the flow and `lib/ci-practice-persistence.ts` owns a separate versioned localStorage checkpoint.

The artifact part of Git/CI state stores three canonical pre-repair evidence snapshots (workflow, producer log, consumer failure), an immutable locked causal hypothesis, selected repair, repair provenance, simulated rerun status, derived verified flag, source-linked explanation and one changed transfer answer. Hypothesis locking requires all three canonical sources. A correct mapping repair can make the simulated pipeline pass after a wrong hypothesis, but verified learning requires both the correct pre-repair `artifact-contract` diagnosis and the minimally sufficient repair.

The first explanation links workflow job-output plumbing to producer artifact `web-dist` and consumer resolution `site-dist`. The transfer changes failure shape: artifact name is aligned, but the archive contains nested `reports/coverage.json`; extraction under `workspace/report` therefore requires the consumer to address `workspace/report/reports/coverage.json`. This is a bounded path-semantics transfer, not proof of general CI mastery.

Git/CI checkpoint schema/fixture are both version 3 and use storage key `holi.devops.git-ci-practice`. Restore validates exact evidence payloads, hypothesis/repair ordering, rerun consistency, verified derivation, bounded reasoning shapes and canonical transfer completion. Linux schema 7 / fixture 5 are unchanged.

Playwright now discovers eight serial Chromium tests: three Linux, two artifact-handoff and three Git revision tests. Artifact tests cover full diagnosis/repair/explanation/transfer persistence and unavailable-localStorage degradation. All still run against the built production app started by Playwright on loopback port 3100.


## Git revision composition after PR #30

lib/git-revision-simulator.ts owns one pure revision state machine plus its changed tag assessment. CiLabState adds revisionPractice; CiLab owns one Git/CI checkpoint and renders GitRevisionLab independently of the artifact exercise. This is bounded composition, not a generic workflow/YAML interpreter. Five exact pre-repair snapshots gate lock/repair. Run stores checkout/metadata SHA; verification stores actual/intended SHA separately and derives verified only from correct pre-repair class AND canonical locked source-linked rationale, minimal repair and both SHA matches. Source IDs/facts and transfer object/target/branch facts validate independently.

Editable explanation/transfer drafts persist, with confirmation revoked on edit; matching unsubmitted drafts remain valid incomplete state. Rebuild/reverification clear downstream work. Revision reset clears only revision; whole-module reset clears both and remounts local hypothesis/repair drafts. Schema 3 adds persisted rationale to the nested shape; fixture 3 changes the pre-repair assessment rubric, without changing incident outputs or tag corpus; v2 and older discard. Linux schema 7/fixture 5 are unchanged. localStorage property getter is safely resolved before helpers so denied getter or methods both degrade to ephemeral practice.



## Pre-repair rationale after PR #32

The single persisted `rationale` field is a bounded editable draft while hypothesis is empty, then a cloned immutable snapshot after class lock. All five source/fact pairs and relation must be nonempty. Lock checks completeness, not correctness; there is no early correctness oracle. Source IDs, facts and relation match independently at verification. Correct repair after bad rationale can match checkout/metadata SHA while verified remains false. Post-repair explanation remains a separate draft and cannot rewrite the pre-repair snapshot. Core edits after lock are inert, and UI disables the entire rationale fieldset. Reset clears it; repair/rebuild/reverify preserve it while revoking downstream confirmations. Wrong complete locked rationale restores as incomplete learning, while malformed/absent locked rationale or contradictory derived flags discard.
